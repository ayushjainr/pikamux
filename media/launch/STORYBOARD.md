# Expert-network cut: Your agent found someone who already knew.

72 seconds. Captions only. HTML/CSS/browser rendering, no video model.
The core selling point is agents discovering and consulting existing expertise.
The board is a supporting human view, not the narrative's protagonist.

## First ten seconds

- 0–3s: An illustrated user task: “Let support staff edit orders.”
- 3–6s: The current agent's search reveals a real expert-card excerpt.
- 6–10s: A real expert-answer excerpt supplies the billing-ownership constraint.
- By 8s the payoff is fully visible: “Your agent found someone who already knew.”

These are designed views with compressed timing, not a continuous recording or
an autonomous-task benchmark. The film-making agent performed the actual Pika
discovery and consultation; the user-task framing is an illustration.

## Recorded discovery and consultation

The synthetic builder from the preceding cut implemented a pure Python support-
dashboard handler, a design note, and five passing tests. Billing owns mutations;
support initially inspects invented orders. No private work projects were used.

One explicit Pika expert refresh interviewed the exact builder in a private side
and populated its card in isolated demo state. No other card was hand-edited.
The film-making agent then ran a real metadata search, pika experts orders --json.
It returned demo-orders with scope/name matches, source availability, selected
topics, artifacts and PARKED status. Discovery made no model call; creating the
card did. There is only one synthetic candidate, not a benchmark of ranking at
scale. A lexical match is not a confidence or intelligence score.

discovery.js contains real selected metadata: an exact scope excerpt, two actual
topics, artifact basenames, actual source/status and match fields. Its designed
card is not claimed to be an existing TUI component. The card's durable scope is
not a current-activity signal. A parked conversation remains useful expertise.

The consultation target was taken from that discovery result's exact native ID,
with provider/source checks. The displayed question is real and omits only this
suffix: “Cite the design artifact. Answer from your earlier work in at most 45
words of plain prose. No tools or file changes.” It does not supply the billing
decision. consultation.js preserves the answer's words, replacing only the
private Markdown link target with the visible filename DESIGN.md.

The answer was independently checked against DESIGN.md. The proposed approach
shown in the film preserves billing ownership and requires authorization,
validation and retry design. It is the film-making agent's evidence-informed
proposal for the illustrated task, not a recorded implementation or proof of a
mistake prevented. It still requires an explicit change of responsibilities and
a billing command contract before edits can be built.

## Preservation and limitations

The recorded consultation completed one turn through the default Pika profile,
then confirmed cleanup complete and discarded true. External scripts compared the
parent transcript SHA-256 and the full demo-project file manifest before/after;
both matched. The parent was parked. Ordinary Pika receipts do not automatically
perform this external hash verification, and no universal preservation guarantee
or simultaneous-coding demonstration is claimed.

Capture uses the local development build with the paginated Codex fork fix from
6b8af0f. That fix is not yet in public v0.5.0a3. Release it before publicly
promoting the affected workflow. The film is not a release announcement.

Separate earlier Codex and Claude cross-server tests support the brief closing
capability note only. This demo is local. OpenCode is supported by the product
but was not exercised in this capture. Native Windows hosting remains unsupported.

## Alchemy decisions

- Show useful knowledge crossing between agents within ten seconds.
- Make the card a reason to choose a peer, not another profile to maintain.
- Reveal a parked expert: value comes from earned context, not a WORKING badge.
- Show the question's consequence in a proposed plan, not just delivered text.
- Make the human a delegator, not the relay between conversations.
- Keep the board as a view into expertise and attention; provider signals, not
  expert-card guesses, determine operational attention.

The strongest three levers are the cold-open exchange, evidence-backed expert
selection, and the answer's consequence. Their success should be tested by
whether viewers can explain who discovers and asks whom after ten seconds.
No measured audience-retention improvement is claimed.

Avoid fictional confidence scores, invented conversations, universal automation
claims, implying every task must consult, or portraying model-based card creation
as free. No push, upload, release or provider-setting change is part of rendering.
